# Context Package (Context L2) Generation & Usage Spec

> Spec version: V2.5
> Document status: Approved (V2.5 final baseline)
> Applicability: development tasks that need an independent Context L2 by risk
> Author: WorkBuddy (delegated by the Coordinator—implemented by Hermes)
> Created: 2026-08-11 (V2.3 finalized)
> Last updated: 2026-08-20
> Reviewer: Richy (approved)

## 1. Positioning

The context package is used for large, long-cycle, multi-agent, or high-risk tasks, to reduce repeated reads and control task boundaries. It is navigation material, not the full set of project facts, the source of truth for requirements, a substitute for design, or proof of exemption from code investigation.

```text
Context L1: the project's existing stable architecture material
  → Context L2: a single-task navigation package generated by risk
  → Context L3: the executor's autonomous investigation of current code and runtime facts
```

Context L3 is the investigation process and code baseline, not another document that must be maintained.

## 2. Context L2 Trigger Conditions

When one or more of the following appear, an independent Context L2 should usually be generated:

- Multi-agent division of labor or a task crossing multiple modules;
- A long-cycle task that may undergo context compression, pause, restart, or execution-instance replacement;
- Many requirement, design decisions, authorization scopes, or compatibility constraints;
- High risk in production entry, concurrency, resource lifetime, persistence, security, or external protocol;
- Parallel tasks needing precise file ownership;
- Reviewer needing to clearly identify stub proof boundaries and open items.

The following usually do not need an independent Context L2:

- A local, low-risk, short-cycle task completed by a single executor;
- A task brief that already fully expresses goal, scope, risk, and verification;
- A context package that merely mechanically copies requirements, design, and task body.

When Context L2 is not generated, the task brief must still contain the necessary baseline, authorization boundary, and stop conditions. Whether to trigger is decided jointly by development track and risk, not solely to save tokens.

## 3. Context L1

- **The standard entry point of Context L1 (physical carrier) is the repository-root `AGENTS.md`**, providing all execution agents with location-predictable, cross-task-stable project-level operating instructions (tech stack, build/test commands, coding conventions, branch strategy, tool permissions);
- `AGENTS.md` supports layering and closest-wins: `global` (user-level) → project root → subpackage-level, the one nearest the file being edited wins; conflict priority is "user's current explicit instruction > closest `AGENTS.md` > remote document";
- Besides `AGENTS.md`, Context L1 may also reuse ADR, architecture documents, coding conventions, or other authoritative material; the generic spec does not force directory and file names;
- Only store cross-task-stable facts and rules that will affect future judgment;
- Detailed history, temporary debugging, task state, and full code lists do not enter Context L1;
- When a formal `AGENTS.md` is missing, authoritative code and documents may be referenced directly; building a new directory set first is not mandatory.

## 4. Minimal Content and Risk Add-Ons

### 4.1 Minimal Content for All Context L2

1. Task goal, risk, and system-integration responsibility;
2. Repository, task branch, worktree, `CodeBaseSHA`, and unambiguous code baseline;
3. Requirements, design, task, and Context L1 references;
4. Verified facts and evidence;
5. Unverified assumptions, open items, and proof gaps;
6. Authorized responsibility or file boundary for modification;
7. Read-only scope that must be autonomously explored;
8. Prohibited behavior and external operations;
9. Verification, Review, invalidation, and stop rules.

### 4.2 Added by Risk

- Key production entry, callers, indirect dependencies, and config paths;
- Lifetime, concurrency, and resource ownership;
- Detailed normal, failure, cancellation, and recovery paths;
- Test-stub "can prove / cannot prove" matrix;
- Precise file ownership;
- Level 0–3 evidence division of labor;
- Recovery points for pause, restart, and execution-instance switch.

Do not fill in task-irrelevant empty sections merely to satisfy the template.

## 5. Facts, Assumptions, and Open Items

- Verified facts must attach a source such as code, config, log, test, or approved decision;
- Assumptions must be falsifiable and state the verification stage;
- Unknown environment, data, credentials, and external behavior must map to `NotRun`, manual verification, or a change request;
- Do not write "the design plans it this way" as "it is already this way now."

## 6. Autonomous Exploration

Context L2 provides only a starting point. The developer must autonomously check by risk:

- Current workspace and review baseline;
- Whether the current task branch, worktree, and `CodeBaseSHA` match the task contract;
- Target interface, implementation, consumers, and related tests;
- Production startup, registration, or actual creation entry;
- Indirect dependencies such as factories, Service Locator, reflection, plugins, `Lazy<T>`, and static state;
- Lifetime, concurrency units, and resource ownership;
- Mock/Fake/in-memory stubs and their proof gaps.

Low-risk tasks may use a concise exploration summary; high-risk tasks should trace at least one success path and one failure path to the system boundary.

When an ordinary local difference is found, it may be corrected within the approved responsibility and reported. Only when the difference affects user behavior, approved design, risk acceptance, or modification permission does it enter `Blocked`.

## 7. Modification and Read-Only Scope

- Authorize modification by default by responsibility or module, allowing directly-related tests and local wiring;
- Parallel conflict, sensitive files, and high-risk resources use a precise file list;
- Read-only investigation may reasonably expand, but must not thereby enlarge modification authorization;
- Modifications beyond the responsibility boundary must first update the task authorization.

## 8. Test-Stub Declaration

Used when there is a material proof gap:

| Replaced dependency | Stub | Real path retained | Can prove | Cannot prove | Subsequent Level |
|---|---|---|---|---|---|

After replacing a production registration entry, lifetime, database Provider, external protocol, or concurrency resource, do not use that test to prove the corresponding real behavior.

## 9. Reviewer's Independent Perspective

- The Reviewer should first form an independent risk model from requirements, actual review target, diff, and code;
- Then read Context L2 to check whether the developer missed facts, open items, or proof gaps;
- Context L2 does not limit the Reviewer's read-only investigation scope;
- The Reviewer should not merely follow the recommended files and risk list inside the package.

## 10. Invalidation Conditions

Context L2 enters `Stale` when the following changes affect the task:

- Requirements, design, task authorization, or Context L1 change materially;
- Related entry, interface, config, or code baseline changes;
- Task branch, `CodeBaseSHA`, dependency state, or merge target changes;
- Facts inside the package are falsified;
- Risk, system-integration responsibility, or modification boundary changes;
- Rework materially changes the original task approach.

Re-validation only needs to update the affected parts and version; mechanical full rewrite is not required.

## 11. Context L1 Reconciliation

- Update Context L1 only when stable architecture, global conventions, core models, authoritative entry, or long-term prohibitions change materially;
- At iteration close, only judge `Changed / NoChange`;
- `NoChange` is recorded in the closeout checklist; no independent development task or Review is created;
- When `Changed`, create a document modification and independently verify accuracy;
- `Changed` must be completed before iteration close, or be approved by the project owner as a follow-up item with ID, owner, and completion time; it must not stay as a conclusion with no owner;
- Do not write unapproved code deviations back into Context L1 in reverse.

## 12. Template

```markdown
# <TASK-ID> Context L2

> Status: Draft / Ready / Stale / Archived
> Risk:
> TaskBranch:
> WorktreePath:
> CodeBaseSHA:
> RequirementsAndDesign:
> ContextL1:
> GeneratedBy:
> ValidatedAt:

## 1. Goal, Risk, and System-Integration Responsibility
## 2. Verified Facts and Evidence
## 3. Unverified Assumptions, Open Items, and Proof Gaps
## 4. Allowed Changes and Must-Explore
## 5. Prohibited Behavior and External Operations
## 6. Key Runtime Paths and Risk Add-Ons
## 7. Test, Review, Invalidation, and Stop Rules
```

## 13. Review Checklist

- [ ] The task genuinely meets the Context L2 trigger condition;
- [ ] No mechanical copying of upstream documents;
- [ ] Facts, assumptions, and open items are separated;
- [ ] Task branch, worktree, CodeBaseSHA, and dependency state match the current task contract;
- [ ] Modification scope does not suppress necessary autonomous investigation and directly-related fixes;
- [ ] Stub proof gaps and system risks are recorded as needed;
- [ ] The Reviewer can form an independent perspective first;
- [ ] Invalidation rules are executable.

## 14. Definition of Done

When the trigger condition holds, the task may use a Context L2 for dispatch only when it binds a valid baseline, exposes open items, provides sufficient exploration routes, and does not substitute for autonomous investigation. When not triggered, a qualified task brief suffices.
